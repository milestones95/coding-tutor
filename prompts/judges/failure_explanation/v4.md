You check a 1–2 sentence explanation of why a LeetCode practice session did not end in an accepted
solution. You will see the person's own account of the failure, the session's condensed timeline
(code snapshots, every run and submit with its result and error text, and the final code), and the
explanation to check.

The person's account is the reference for why it failed. The timeline is the reference for what
happened: code, inputs, outputs, errors, test counts and timings.

Failure types:
- wrong_approach (a flawed algorithm): the idea itself is wrong. Even a perfect implementation of it
  gives wrong answers, for example greedy where the problem needs DP, or binary search on unsorted
  data. The fix is to change the approach
- implementation_bug: the idea is correct, but the code doesn't faithfully carry it out. The fix is
  to change a line or two. It may break many inputs, or only unusual ones (an edge case bug: an empty
  array, a single element, all duplicates, overflow) while normal inputs work
- too_slow: the approach works but its time or memory use is too high
- did_not_finish: the session ended without a submit

Person's account:
- Failure type: $failure_type
- Key facts: $key_facts

Grade each item on its own. For each one, first give a one-sentence reason, then `met`.

1. consistent — The cause the explanation gives agrees with the person's failure type and key
   facts. It may use other words and name more detail. It is not met when it blames a different
   kind of cause. The main line is one question: would a perfect implementation of the idea in the
   final code still give wrong answers?
   - the account says wrong_approach, but the explanation blames an edge case, a small bug or speed
     (it treats the idea as workable once the code is fixed): not met;
   - the account says the idea was workable (implementation_bug, too_slow), but the explanation
     says the idea, approach or algorithm itself does not work, or that the fix is a different
     approach: not met, even if it also names real lines of code. Saying the algorithm fails or
     doesn't solve the problem, without placing the cause in a fixable mistake in the code, blames
     the idea. How many inputs a bug breaks does not decide this: a bug that breaks ordinary inputs
     and a bug that breaks only an edge case are both implementation_bug;
   - the account says did_not_finish: met when the explanation's cause agrees with the key facts
     (what was left unfinished or still broken when the session ended); not met when it blames a
     different kind of cause than the key facts give.
2. no_invented_cause — Every concrete detail in the explanation (a line of code, an input, an
   output, an error, a test count, a size) appears in or follows directly from the timeline, and
   the cause it names is visible there. A general statement about the approach (its complexity,
   what kind of input breaks it) is not a detail. One invented or wrong detail means not met.
   A specific input, output or value counts only if it is written in the timeline. Working out an
   input from an output, or quoting a test case the timeline never shows, is invented, even if it
   is probably right.

Timeline:
$timeline

Explanation to check:
$explanation

Answer with JSON only:
{"consistent": {"reason": "...", "met": true|false},
 "no_invented_cause": {"reason": "...", "met": true|false}}
